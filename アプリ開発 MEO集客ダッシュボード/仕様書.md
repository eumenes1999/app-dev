# MEO集客ダッシュボード 仕様書（2026-08-12作成）

## 概要

MEO（マップエンジン最適化／Googleビジネスプロフィール集客）の月次レポートを模した、練習用のデータ可視化アプリ。ダミーの集客指標を月単位で入力し、D3.jsで折れ線・棒グラフに可視化する。「新しい技術（D3.js／本格的なデータ可視化）に触れる練習」を目的に、100日習慣トラッカー・家計簿と同じSupabaseプロジェクトを共有する形で作成した。

- リポジトリ: `eumenes1999/app-dev`（GitHub Pages、`main`ブランチ直下から配信）
- ローカルファイル: `04_アプリ開発/アプリ開発 MEO集客ダッシュボード/`

## デザイン方針：dataviz skillに準拠

このアプリのグラフは、社内の`dataviz` skill（`references/`配下に手順・パレット・マーク仕様がまとまっている）の手順をそのまま適用して作った。骨子は以下の通り。

1. **色より先に「グラフの種類」を決める** — 「表示回数の推移」は時系列比較なので折れ線、「最新月のアクション内訳」は少数カテゴリの大小比較なので棒グラフ、という具合に、データの「仕事」から逆算して形式を選ぶ
2. **カラーパレットは検証済みの参照パレットをそのまま使用** — skillの`references/palette.md`に載っている8色のカテゴリカルパレット（スロット1〜3: blue `#2a78d6` / aqua `#1baf7a` / yellow `#eda100`、ダーク版は `#3987e5` / `#199e70` / `#c98500`）を採用。`scripts/validate_palette.js`でCVD（色覚多様性）安全性とコントラストを実際に検証してから実装した
3. **マーク仕様を固定値で統一** — 線は2px・端は丸め、マーカーは半径4px＋2pxの背景色リング、棒は幅上限24px・上端4px丸め、グリッド線は1pxのヘアラインで控えめに、というskillの規定値をそのまま使用
4. **ラベルは「選択的に」** — 折れ線は各系列の最終値だけを直接ラベル表示（全点にラベルを打たない）、棒グラフは3本しかないので全部にキャップ上ラベル。凡例は2系列以上で常時表示
5. **ホバー層は標準搭載** — 折れ線はクロスヘア（縦線）+ 全系列の値をまとめたツールチップ、棒グラフは棒ごとの`pointerenter/pointermove/pointerleave`ツールチップ。キーボードフォーカスでも同じ情報が出るようにしている
6. **ダーク/ライム両対応** — チャートの色・グリッド線・文字色はすべてCSSカスタムプロパティ（`--series-1`等）経由で参照し、`getComputedStyle`でJS側に渡す設計。`@media (prefers-color-scheme: dark)`で自動切り替え（このアプリには手動トグルは無い）

## 画面構成

単一ページ構成（タブ分けなし）。上から順に：

1. **月次データ入力フォーム** — 対象月（`<input type="month">`）＋7つの数値項目
2. **KPIタイル行**（4枚）— 検索表示回数・マップ表示回数・アクション数合計・平均評価。いずれも直近月の値と前月比（件数＋%、良化=緑／悪化=赤）を表示
3. **表示回数の推移（折れ線グラフ）** — 検索表示回数とマップ表示回数の2系列を月次で比較
4. **最新月のアクション内訳（棒グラフ）** — サイトクリック／電話タップ／ルート検索の3カテゴリを比較
5. **月別レコード一覧（テーブル）** — 全項目を一覧表示、行ごとに削除可能

## 機能一覧

### データ入力

- 対象月＋7項目（検索表示回数・マップ表示回数・サイトクリック数・電話タップ数・ルート検索数・クチコミ新規獲得数・平均評価）を入力して保存
- 同じ月に再度保存すると**upsert**（`onConflict: 'user_id,month'`）で上書きされる。二重入力にはならない
- 数値未入力の項目は0扱い（平均評価のみ空欄可＝null）

### KPIタイル

- 直近月の値と前月比を自動計算。差分が正なら「good」（緑）、負なら「critical」（赤）、前月データが無ければ「neutral」（グレー）
- 平均評価は%ではなく差分の実数（例: `+0.2 前月比`）で表示

### グラフ

- 折れ線グラフ：クロスヘア追従＋ツールチップ（ポインター位置に最も近い月を自動選択）、系列ごとに凡例と終点ラベル
- 棒グラフ：バーごとのホバー/フォーカスでツールチップ、キャップ上に値ラベル
- データが0件のときはグラフを隠し、代わりに案内文を表示

### レコード管理

- 月別一覧をテーブルで表示（新しい月が上）
- 行ごとに削除ボタン（確認ダイアログあり、楽観的UI＋失敗時ロールバック）

## データベース設計（Supabase / Postgres）

スキーマ全文は同フォルダの`supabase_schema.sql`を参照。

### `meo_reports`テーブル

| カラム | 型 | 備考 |
|---|---|---|
| id | uuid | PK |
| user_id | uuid | `auth.uid()`がデフォルト、`auth.users`参照、cascade delete |
| month | date | 対象月の1日で保存（例: `2026-08-01`） |
| search_impressions | int | 検索表示回数 |
| map_impressions | int | マップ表示回数 |
| website_clicks | int | ウェブサイトクリック数 |
| phone_taps | int | 電話タップ数 |
| direction_requests | int | ルート検索数（来店誘導） |
| new_reviews | int | クチコミ新規獲得数 |
| avg_rating | numeric(2,1) | 平均評価（null許容） |
| created_at | timestamptz | |

- `unique index (user_id, month)`（非部分インデックス）でupsertの衝突キーに使用
- RLSポリシー: select/insert/update/delete、いずれも`auth.uid() = user_id`

## 実装上の注意点・学び

1. **`ON CONFLICT`は非部分ユニークインデックスで組む** — 100日トラッカーの`habit_memos`で踏んだ「部分インデックス（`where habit_id is not null`）だとPostgRESTのupsertが失敗する」という学びをそのまま適用し、`meo_reports`は最初から通常のunique indexで設計した（同じ轍を踏まずに済んだ）
2. **`<input type="month">`への自動テスト入力は要注意** — E2Eテスト（puppeteerのfill操作）で`type="month"`の入力欄に値を流し込むと、既存値の上に新しい文字が変な形で挿入され、`"202606-08"`のような壊れた値になることがあった。実ユーザーがネイティブの月ピッカーUIを操作する分には起きないテストツール側の挙動だが、自動テストでは`element.value = '2026-06'; element.dispatchEvent(new Event('change'))`のようにDOM APIで直接値を設定する方が確実
3. **データの「仕事」から形式を選ぶと、色の話をする前に大半の設計判断が終わる** — dataviz skillの手順通り「これは推移の比較か、内訳の比較か」を先に決めてから色・マーク仕様に進んだことで、手戻りなく一発で実装できた
4. 楽観的UI＋失敗時トースト＋ロールバックのパターン（100日トラッカーで確立した設計）は、このアプリでも保存・削除の両方にそのまま流用した
