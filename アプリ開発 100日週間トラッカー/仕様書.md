# 100日習慣トラッカー 仕様書（2026-08-01作成 / 2026-08-12更新）

## 概要

「100日チャレンジ」形式の習慣トラッカーPWA。最大10個の習慣を登録し、日々チェック/スキップを記録して継続を可視化する。ビルドステップなしの素のHTML/CSS/JS + Supabase（Postgres + Auth）構成。

- 公開URL: https://eumenes1999.github.io/app-dev/アプリ開発%20100日週間トラッカー/index.html
- リポジトリ: `eumenes1999/app-dev`（GitHub Pages、`main`ブランチ直下から配信）
- ローカルファイル: `04_アプリ開発/アプリ開発 100日週間トラッカー/`

## 技術構成

| 層 | 内容 |
|---|---|
| フロント | 素のHTML/CSS/JS（`index.html` / `styles.css` / `app.js`）、ビルド不要 |
| バックエンド | Supabase（Postgres + Auth）。`家計簿`アプリと同一プロジェクトを共有（無料枠温存のため。詳細は`04_アプリ開発/開発ナレッジ/Supabase無料枠運用ルール_2026-08-01.md`） |
| 認証 | 匿名ログイン（`supabase.auth.signInAnonymously()`）。ログイン画面なし、端末ごとに自動でセッション発行 |
| ホスティング | GitHub Pages（`eumenes1999/app-dev`リポジトリ、publicリポジトリの標準機能） |
| ライブラリ | `@supabase/supabase-js@2`（esm.sh経由でCDN import）、`canvas-confetti`（jsdelivr CDN） |

### 認証を匿名ログインにした経緯

当初はメール/パスワード認証で実装したが、以下の問題が連続したため方針転換した。

1. Supabase無料枠の組み込みSMTPはメール確認リンクにGmailなどのリンク事前読み込み（セキュリティスキャン）が絡むと、本人がクリックする前にワンタイムトークンが失効する
2. Confirm email設定のダッシュボード上の場所がSupabaseのUI変更で分かりにくくなっていた
3. パスワードリセットのメール送信がレート制限に引っかかった

個人の習慣トラッカーというユースケースでは「複数端末で同じデータを見たい」以上の認証要件（他人との共有、パスワードリセット等）が不要なため、匿名ログインに統一。ただしこの方式は**端末のブラウザストレージが消えるとそのデータには二度とアクセスできない**トレードオフがある。このリスクへの対策として、設定タブに手動のJSONバックアップ機能（エクスポート/インポート）を追加済み（詳細は「機能一覧 > 設定」参照）。

## 画面構成

ヘッダー（グラデーションのヒーローセクション、見出し・補足文は編集可能）＋ 3つのタブで構成。

1. **習慣**（デフォルト表示）— 習慣カードの一覧。カードごとに色スウォッチ・達成日数・連続日数・達成率・100マスグリッド・今日のアクションボタン・今日のメモ欄を表示
2. **メモ** — 習慣ごとのメモ閲覧・編集画面（週次エディタ＋恒久アーカイブ）
3. **設定**（⚙️アイコン）— トップページ文言・背景画像・テーマ・データのバックアップ・データリセットをまとめた画面

## 機能一覧

### 習慣（メイン画面）

- 目標（習慣）の追加（最大10個、30文字まで）
- 今日の分をチェック（達成）／スキップ（お休み）／取り消し
  - チェック操作は**即座に画面へ反映**してから裏でSupabaseに保存する楽観的UI。保存に失敗した場合のみロールバックし、画面上部にトースト通知を出す
  - 操作した直後のカードだけポップアニメーションが入る
  - チェックが成功すると、20パターン用意したポジティブな一言（「その調子、いい流れ！🔥」等）からランダムで1つをトースト表示する。「また明日も続けたくなる」ことを狙った演出
- 連続日数（streak）: 今日 or 昨日を起点に遡ってカウント。スキップ日は連続を途切れさせないが、加算もしない
- 100日ぶんのマス目グリッド（達成日=白、未達成の過去日=薄い、スキップ日=半透明、今日=枠線、未来日=さらに薄い）
- カード背景色のカスタマイズ：8色プリセット（pink/purple/orange/green/blue/teal/red/indigo）のスウォッチをカード上部に表示し、タップで即切り替え。同じ色をもう一度押すと未指定（自動ローテーション表示）に戻る
- カード内に「今日のメモ」欄をインライン表示（メモタブと同じデータ・同じ保存処理を共有。どちらで書いても即座に両方へ反映される）
- 習慣の削除
- 紙吹雪演出（達成時、canvas-confetti）

### メモ

- 習慣ごとに1日1件のメモ
- **直近7日分だけ編集可能**（今日から6日前まで、テキストエリアでインライン編集、blur時に自動保存）
- それより古いメモは「過去のメモ」として閲覧専用アーカイブに表示
- 習慣セレクタで「すべて（閲覧のみ）」を選ぶと、全習慣ぶんのメモを横断して閲覧できる（編集不可）
- **習慣本体を削除・全データリセットしても、そのメモは消えない**。`habit_memos`テーブルは`habits`テーブルと独立したライフサイクルを持ち、習慣削除時は`habit_id`が`null`になるだけで行自体は残る（`habit_title`を書いた時点でスナップショットしているため、習慣が消えてもメモ側で何のメモか分かる）

### 設定

- **トップページの文言編集**：見出し（h1、24文字まで）・補足文（36文字まで）を自由に変更可能。端末のローカルストレージに保存し、未入力時は既定の文言をデフォルト表示
- 背景画像の選択（端末のローカルストレージに保存、同期はしない）
- 背景画像をデフォルトに戻す
- テーマ切り替え（ダーク/ライト、未選択時はOS設定に追従）
- **データのバックアップ（エクスポート/インポート）**：習慣・メモをまとめてJSON形式で書き出し・読み込みできる。匿名ログインは端末のブラウザストレージが消えると復元不能なため、その対策として追加。インポートは既存データへの追加という扱いで、習慣は新規idで挿入、メモは対応する新idに紐付け直す（同名メモの重複を弾く仕組みは無いので、同じバックアップを二重に読み込むと重複登録される点に注意）
- 全データリセット（習慣のみ削除。メモは前述の通り残る）

## データベース設計（Supabase / Postgres）

スキーマ全文は同フォルダの`supabase_schema.sql`を参照。RLSは全テーブルで`auth.uid() = user_id`を基本とし、本人のデータ以外にはアクセスできない。

### `habits`テーブル

| カラム | 型 | 備考 |
|---|---|---|
| id | uuid | PK |
| user_id | uuid | `auth.uid()`がデフォルト、`auth.users`参照、cascade delete |
| title | text | 習慣名 |
| completed_dates | date[] | 達成日の配列（ISO日付文字列） |
| skipped_dates | date[] | スキップ日の配列 |
| color | text | カード背景色のプリセットキー（pink/purple/orange/…）。null なら自動ローテーション表示 |
| created_at | timestamptz | 100日グリッドの起点（day1）として使う |

RLSポリシー: select/insert/update/delete、いずれも`auth.uid() = user_id`。

### `habit_memos`テーブル

| カラム | 型 | 備考 |
|---|---|---|
| id | uuid | PK |
| user_id | uuid | `auth.uid()`がデフォルト |
| habit_id | uuid | `habits.id`参照、**on delete set null**（habits削除時にメモは残る） |
| habit_title | text | 記入時点の習慣名スナップショット |
| date | date | メモの対象日 |
| content | text | 本文 |
| created_at / updated_at | timestamptz | |

- `unique index (habit_id, date)`（非部分インデックス）でupsertの衝突キーに使用。Postgresは`NULL`同士を重複と見なさないため、習慣削除後のオーファン行同士が誤って衝突することはない
- RLSポリシー: select/insert/update のみ。**delete ポリシーは意図的に用意していない**（メモは書いたら消えない設計にするため、アプリ側からもDELETEは一切発行しない）

## 実装上の注意点・ハマったポイント

今後似た機能を他アプリで作る際の参考として記録。

1. **`hidden`属性とCSSの`display`指定が競合する**: 要素に`hidden`属性を付けても、同じ要素（または同じクラス）に`display: flex`等を直接指定していると、CSSの詳細度次第でUAスタイルの`display: none`が負けて表示されたままになる。グローバルに`[hidden] { display: none !important; }`を入れて解決
2. **PostgRESTのON CONFLICTと部分ユニークインデックスの相性が悪い**: `create unique index ... where habit_id is not null`のような部分インデックスは、`upsert(..., { onConflict: 'habit_id,date' })`のターゲットとして認識されず`there is no unique or exclusion constraint matching the ON CONFLICT specification`エラーになる。通常の（部分でない）unique indexなら、Postgresの仕様上NULL同士は元々重複と見なされないため、部分インデックスにする必要自体がなかった
3. **カラム追加のマイグレーション漏れは「保存が静かに失敗する」形で現れる**: `skipped_dates`カラムをDBに追加し忘れた状態でも、楽観的UI＋ロールバックの実装だと画面は一瞬反映されたように見えてすぐ元に戻るだけで、エラーが目に見えない。保存失敗時に必ずトースト通知を出すようにして解消
4. Supabaseの無料枠は組み込みメール送信のレート制限が厳しいため、個人用途で認証機能を作る際は最初から匿名ログインを検討する方が手数が少ない
5. **匿名ログインの弱点（端末ストレージ消失＝データ消失）は、複雑な仕組みを足さずJSONエクスポート/インポートだけで実用上十分にカバーできる**。匿名アカウントを本アカウント化する手段（`updateUser()`でのメール紐付け）も検討したが、過去に苦労したメール確認の摩擦を再び背負うことになるため見送った。「使う側に定期的な手動操作を求める」割り切りと、「認証まわりの複雑さを増やさない」判断のトレードオフ

## デザインシステム上のノウハウ（Apple Health風リデザイン）

Apple Healthの雰囲気（彩度の高いグラデーション、大きく力強い見出し）を参考に、ネオブルータリズム系（黒縁・ハードシャドウ）から現在の配色に刷新した際の設計判断。

5. **テーマ（ダーク/ライト）はCSSカスタムプロパティの丸ごと差し替えで実装**: `:root[data-theme="dark"]` / `:root[data-theme="light"]`で変数セットを切り替え、未選択時は`@media (prefers-color-scheme: dark)`でOS設定に追従させる。初期表示のちらつき（FOUC）を防ぐため、`<head>`内・スタイルシート読み込み前に、localStorageの保存値を先に`data-theme`へ反映する小さいインラインスクリプトを置いている
6. **カード内テキスト色は`header`/`.goal-card`セレクタ内で`--text-secondary`をローカル上書き**することで、「ヒーロー領域や色付きカードは常に白文字、それ以外はテーマに応じた文字色」を同じ変数名のまま両立させている（グローバルな上書きだと、カードが無い＝ページ地の背景に直接乗る空状態メッセージの文字色が読めなくなる問題があった）
7. **目標カードの配色はCSSのみで自動ローテーション**: `.goal-card:nth-child(5n+1)`〜`(5n+5)`に5パターンのグラデーションを割り当てているだけで、JS側で色を管理する必要がない。Apple Healthアプリ本体のカテゴリカラー（心臓=赤、睡眠=紫など）を意識した配色
8. **Appleらしいタイポグラフィは、太さを上げるほど遠ざかる**: 直感的には見出しや大きい数字表示を800〜900(Black)にしたくなるが、実際のAppleのUIは700(Bold)止まりで、字間(letter-spacing)を締めることで力強さを出している。数値表示には`font-variant-numeric: tabular-nums`を付けると、桁が変わっても幅がガタつかず落ち着いて見える
