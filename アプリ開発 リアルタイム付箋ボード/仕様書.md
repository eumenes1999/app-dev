# リアルタイム付箋ボード 仕様書（2026-08-14作成）

## 概要

Supabase Realtimeの練習用アプリ。ひとつの共有キャンバス上に付箋(ふせん)を追加・移動・編集・削除でき、その変更が他のブラウザタブ/セッションにリアルタイムで反映される「共同編集ホワイトボード」のミニ版。「新しい技術（Supabase Realtimeの3機能: Presence／Broadcast／Postgres Changes）に触れる練習」が目的で、100日週間トラッカー・家計簿・MEO集客ダッシュボードと同じSupabaseプロジェクトを共有する形で作成した。

一人でも検証できる設計（詳細は「検証方法」参照）：複数のブラウザタブ/プロファイルを開けば、それぞれが匿名ログインで別ユーザーとして扱われ、擬似的に複数人での共同編集を再現できる。

### このアプリで新しく練習する技術：Supabase Realtimeの3本柱

他の練習アプリ（トラッカー・家計簿・MEOダッシュボード）はいずれも「ページを開いたときに一度データを読み込む」だけの単発フェッチ型だった。このアプリでは、Supabase Realtimeが提供する3つの仕組みをそれぞれ用途別に使い分ける。

1. **Postgres Changes（DB変更の購読）** — `sticky_notes`テーブルへのINSERT/UPDATE/DELETEを`postgres_changes`でリアルタイム購読し、他セッションが行った付箋の追加・確定した移動・削除を即座に画面へ反映する。**確定した状態**の同期に使う
2. **Presence（在室・接続状態の共有）** — ボードを開いている全セッションが`channel.track()`で自分の存在（ユーザーID・割当色）を通知し合い、「今何人がこのボードを見ているか」をバッジ表示する。**誰が繋がっているか**の同期に使う
3. **Broadcast（一時的なイベント配信）** — 付箋をドラッグ中の座標や、マウスカーソル位置を`channel.send({type:'broadcast', ...})`で高頻度に送り合う。DBに書き込むほどではない**一時的・確定前**の状態同期に使う（ドラッグ確定時だけPostgres Changes側＝DB更新に反映する）

## デザイン方針

- 他の練習アプリと同じCSSカスタムプロパティ方式（`--surface-1`等）でダーク/ライト自動切替に対応する。ただし付箋の色（黄・ピンク・青など）自体は現実の付箋紙と同じ発想で、ダーク/ライトどちらでも変わらない固定パレットにする（背景・文字色などUIクロームだけがテーマに追従する）
- カードベースのヘッダー・トースト・初期化エラー表示など、既存アプリと共通のUI言語を踏襲する
- キャンバス部分は既存アプリの`max-width: 720px`の縦積みカードとは異なり、画面幅いっぱいに近い「開いた作業スペース」として設計する（付箋を自由に配置するため）

## 機能一覧

### 付箋の操作

- 「＋ 付箋を追加」でランダムな位置・わずかなランダム回転・自分の割当色で新規付箋を作成（DBにinsert、楽観的UIで即描画）
- 付箋をドラッグして移動。ドラッグ中はBroadcastで他セッションにも位置をリアルタイム中継し、ドロップ時にDBへ確定位置を書き込む（Postgres Changes経由で全セッションに伝播）
- 付箋のテキストをクリックして編集。フォーカスが外れたタイミング（blur）でDBに保存
- 付箋ごとに削除ボタン（確認ダイアログなし、楽観的UI＋失敗時ロールバック。付箋は消えても実害が小さいため確認ダイアログは省略）

### 共同編集の可視化

- 在室人数バッジ：現在ボードを開いている人数と、それぞれに割り当てられた色のドットを表示（Presence）
- 他セッションのカーソル：他の人がボード上でマウスを動かすと、その人の割当色で小さなカーソル表示が動く（Broadcast、間引き送信）
- 他セッションが付箋を追加・移動・削除すると、リロード不要で自分の画面にも即座に反映される（Postgres Changes）

### AIによる要約(2026-08-14追加)

- ツールバーの「✨ AIで要約」ボタンを押すと、その時点でボード上にある全付箋のテキストをSupabase Edge Function経由でClaude API(`claude-haiku-4-5`)に送り、3〜5行程度の要約をパネル表示する
- **Anthropic APIキーはクライアントに置かない。** Supabase anon keyと違い、Anthropic APIキーは公開前提の鍵ではない（RLSのような保護機構が無く、盗まれると他人がその枠でAPIを使い放題になる）ため、Edge Functionをプロキシとして挟み、キーはSupabaseのシークレットとしてサーバー側にのみ保管する
- 空の付箋(本文が空文字)は要約対象から除外する。付箋が1件も無い場合はAPIを呼ばず「要約する付箋がまだありません。」を即時表示する
- デプロイ・APIキー設定はユーザー側の作業が必要(下記「デプロイ手順」参照)。未デプロイの状態でボタンを押すと、失敗トーストではなく要約パネル内にエラーメッセージが表示される(グレースフルデグレード)

## Supabase Edge Functionsのデプロイ手順(AI要約機能を使う場合)

`supabase/functions/summarize-notes/index.ts`はコードとして用意済みだが、以下はSupabaseダッシュボード/CLI側でユーザーが行う必要がある(Claude CodeからSupabaseへ直接デプロイする経路は無い)。

1. [console.anthropic.com](https://console.anthropic.com)でAnthropic APIキーを発行する
2. [Supabase CLI](https://supabase.com/docs/guides/cli)をインストールし、`supabase login`でログイン
3. このアプリのフォルダ(`アプリ開発 リアルタイム付箋ボード/`)で`supabase link --project-ref <プロジェクトref>`を実行してプロジェクトに紐付ける(プロジェクトrefはSupabaseダッシュボードのURLやプロジェクト設定から確認できる)
4. `supabase secrets set ANTHROPIC_API_KEY=sk-ant-...`でAPIキーをシークレットとして登録する
5. `supabase functions deploy summarize-notes`でEdge Functionをデプロイする

デプロイ後は、アプリ側の追加設定は不要(`app.js`は`supabase.functions.invoke('summarize-notes', ...)`で呼び出す実装が最初から入っている)。

スキーマ全文は同フォルダの`supabase_schema.sql`を参照。

### `sticky_notes`テーブル

| カラム | 型 | 備考 |
|---|---|---|
| id | uuid | PK |
| created_by | uuid | `auth.uid()`がデフォルト、`auth.users`参照、cascade delete |
| text | text | 付箋の本文 |
| color | text | 付箋の色キー（yellow/pink/blue/green等） |
| x | numeric | ボード内の横位置（%、0〜100） |
| y | numeric | ボード内の縦位置（%、0〜100） |
| rotation | numeric | わずかな傾き（度） |
| updated_at | timestamptz | |

**RLS方針が他アプリと根本的に異なる点に注意：** 100日トラッカー・家計簿・MEOダッシュボードは「`auth.uid() = user_id`で自分のデータしか見えない」プライベートなデータ分離だったが、このアプリは**全員で同じボードを共同編集する**のが目的のため、`select`は`using (true)`で全員に公開し、`insert`/`update`/`delete`も「匿名ログイン済みであれば誰でも」許可する（他人の付箋を移動・削除できる、が意図した挙動）。プライバシー分離ではなく「認証済みユーザーのみアクセス可」という緩いガードのみを置く設計。

## 実装上の注意点・学び（着手前の設計メモ）

1. **確定データ(DB)と一時データ(Broadcast)を分離する** — ドラッグ中の座標を毎フレームDBに書き込むと書き込み過多になるため、ドラッグ中はBroadcastのみで他セッションに中継し、ドロップ時に1回だけDBへ書き込む（Postgres Changes側の`updated_at`もそこで更新される）
2. **自分自身が発信したPostgres Changesイベントで自分の操作がガクつかないようにする** — 自分でドラッグ確定・編集した直後にPostgres Changesの購読コールバックが自分にも返ってくるため、ローカルの状態と食い違わない限りは再描画をスキップするか、同一内容なら上書きしても見た目が変わらないようにする
3. **RLSは「プライベート分離」と「公開共有」の2パターンがあることを型として持っておく** — 既存3アプリの`auth.uid() = user_id`パターンをそのまま使い回さず、このアプリでは`using (true)`の共有ボード型を採用する（[[supabase_free_tier_shared_project]]の運用ルール自体は変わらず、あくまでRLSポリシーの中身が違うだけ）
4. **検証（puppeteer等での自動確認）は複数ブラウザプロファイルを同時に開いて行う** — 匿名ログインはブラウザプロファイル単位で別ユーザーになるため、2つ以上のプロファイルを同時起動し、片方の操作がもう片方に伝播することを見て確認する。MEOダッシュボードのブラッシュアップで判明した「ESMモジュールのブラウザキャッシュ」問題（コード変更後の再ナビゲートだけでは反映されないことがある）も踏まえ、キャッシュ無効化オプション付きで検証すること
5. **Postgres ChangesとPresence/Broadcastでは「同時接続の持続性」の要求が違う** — Postgres Changesはサーバーが検知して全購読者にpushするため、片方が一瞬再接続してもDBの整合性さえ取れていれば反映される。一方Presence/Broadcastはクライアント同士がリアルタイムサーバー経由で直接メッセージをやり取りするため、双方が文字通り同時に接続し続けている必要がある。実際の検証では、puppeteer MCP経由の複数エージェント並行操作で片方のnavigate操作がもう片方のブラウザプロセスを予期せず再起動させてしまい、「在室人数バッジが常に1のまま」という現象が起きた。`presence`イベント(join/sync/leave)と`track()`の戻り値を一時的にログ出力して調べたところ、発火自体は正しいペイロードで機能しており、アプリのバグではなく「自動テストツールが2つの独立したブラウザセッションを同時に維持できていなかった」というテスト手法側の限界だと判明した。Presence/Broadcastの「複数人が同時に見えるか」を最終確認したいときは、自動化に頼らずユーザー自身が本物のブラウザウィンドウを2つ並べて手動確認するのが確実
